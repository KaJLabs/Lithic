# Disabled native-gateway boundary candidate — 2026-10-01

Status: **isolated engineering evidence only**. This is not a Makalu
deployment, validator acceptance, production gas-price approval, or gateway
activation. It used the Foundation-approved isolated 13-vCPU/78-GB/350-GB
benchmark VPS, GoLevelDB/IAVL, and the native `StateDB` harness. It did not
execute full blocks, durable `lithod` commits, public RPC, or live consensus.

The boundary harness and fixture were committed as Lithic
`bccb38d` (`test(lithovm): exercise durable deploy and log boundaries`). The
isolated working copy used that test/fixture over the prior pinned Lithic
source; its compiler and FFI were already built from that source. The test is
opt-in and leaves the disabled gateway unregistered. No LAX, production
contract, or MultX state was changed.

| Generated bytecode | Gateway admission | Execution at 10M native gas | Gas used |
| ---: | --- | --- | ---: |
| 4,096 bytes | accepted | deployed and committed | 5,560,231 |
| 16,384 bytes | accepted | out of gas, no state/log leak | 10,000,000 |
| 32,768 bytes | accepted | out of gas, no state/log leak | 10,000,000 |
| 65,536 bytes | accepted | out of gas, no state/log leak | 10,000,000 |
| 65,537 bytes | rejected | not executed | — |

These are synthetically sized, compiler-generated contracts, not Finance/LAX
workloads. Gateway admission is a bytecode-envelope check, **not proof of
deployability**. Under the provisional 20,000-gas per additional rounded
32-byte growth unit and 10M native cap, even the 16-KiB candidate cannot
deploy. Do not advertise 64-KiB deployability or production affordability
from the current admission limit. Neither the growth rate nor the cap has
final policy approval.

Each dynamic event occupies 4,106 envelope bytes including encoding overhead;
15 events occupy 61,590 bytes, while 16 would occupy 65,696 bytes and exceed
the 65,536-byte output envelope. The failure was confirmed as an execution
revert with the expected dynamic-output-limit message. The logged gas amounts
are disabled-candidate values; the test does not establish log throughput in
full blocks.

Reproduction from a pinned Linux checkout with `lithc` and `lithovm-ffi`
built:

```sh
cd integration/native-chain
LITHOVM_BOUNDARY_BENCH=1 go test -mod=mod -tags lithovm_chain_lab \
  -run '^TestDurableDeploymentAndLogBoundariesCandidate$' -count=1 -timeout 20m -v .
go test -mod=mod -tags lithovm_chain_lab -count=1 -timeout 20m ./...
```

Both commands passed on the isolated VPS. The boundary run took 5.27 seconds;
the complete tagged native-chain suite took 1.45 seconds. Single-call timings
from this smoke are deliberately not interpreted as p50/p95/p99 validator
performance.

The remaining required acceptance work is a **real full-block** benchmark on
the isolated `lithod` configuration at multiple utilization levels through
the live Makalu block-gas ceiling, including warm/cold state, durable commits,
maximal logs, failed/OOG calls, and p50/p95/p99 execution and commit time with
CPU/RSS, DB I/O, and persistent growth. Production gas economics also need a
policy for the admission/deployability mismatch, final source pinning, and
independent security retesting. This run grants no approval for registration,
activation, or deployment.
