# LEP100-15 signing profile proposal

Research date: 2026-11-05. Status: **one concrete proposal for standards-owner review; unapproved and unimplemented**. Suggested review identifier: `LEP100-15-EIP712-1`. That identifier does not register a standard or establish conformance.

## Recommendation and evidence boundary

Adopt the draft-native transaction model below using EIP-712 hashing, Keccak-256, Ethereum-width addresses, strict secp256k1 signatures, and a separately specified contract-verifier interface. Preserve every authorization field in the draft, including operation, policy hash and metadata hash. Freeze the entire profile and its vectors in one owner decision; implementations must not choose among alternatives independently. The release explicitly lists all 12 choices as unresolved and prohibits a signing-interoperability or production-conformance claim until they are frozen. [L1]

This proposal has **no byte-compatibility claim with the existing Litho Vault EVM signing format**. Its vendored SDK is useful implementation evidence for hashing, wallet integration and strict signature rules, but it signs a different structure. The SDK domain is `LithoVault`/`1`; its `Approval` includes `proposalId`, calls, `metadataHash`, `executableAt`, `validUntil` and `configEpoch`. Its calls contain target, value and data, with no operation. The proposed domain is `LEP100-15`/`1`, and the transaction also binds account, chain ID, nonce, operation and policy hash. Existing Vault approvals cannot be copied, converted or relabeled as signatures of the new digest. [L4, L5]

The supplied client draft and release draft have identical 3,847-line text after UTF-8 BOM/newline normalization. Their raw SHA-256 values differ: release `c6383033e8b8e2ad300ef07149f3929f355744ca3c9484f370ac4f30058198bf`; client `01d0638997f5abd12f6d8ee463f82b4e155fc0c591923d85fb7aad8a5d9e0b1b`. The release checkout read for this note reports HEAD `3873efb47e419b6684c2ea206c84c7e18bc1c8ae`. No accepted signing decision was found in the reviewed Lithic release/closure evidence. That is a bounded search finding, not proof that no decision exists elsewhere. [L2, L3, L6]

## Exact proposed preimages

The following quoted type strings are exact, ASCII/UTF-8, with no newlines or extra spaces. `abi.encode` means the typed Solidity ABI encoder, not `abi.encodePacked`. Identifiers in wallet typed data use the camelCase names shown here; native draft snake_case fields map to them once before encoding.

```text
DomainType = "EIP712Domain(string name,string version,uint256 chainId,address verifyingContract)"
CallType = "Call(address target,uint256 value,bytes data,uint8 operation)"
TxType = "MultiSigTransaction(address account,uint256 chainId,uint256 nonce,Call[] calls,uint64 validAfter,uint64 validUntil,bytes32 policyHash,bytes32 metadataHash)Call(address target,uint256 value,bytes data,uint8 operation)"

encodedDomain = abi.encode(K(DomainType), K("LEP100-15"), K("1"), chainId, account)
domainHash = K(encodedDomain)

encodedCall[i] = abi.encode(K(CallType), target[i], value[i], K(data[i]), operation[i])
callHash[i] = K(encodedCall[i])
encodedCallList = callHash[0] || ... || callHash[n-1]
callsHash = K(encodedCallList)

encodedTransaction = abi.encode(K(TxType), account, chainId, nonce, callsHash,
                                validAfter, validUntil, policyHash, metadataHash)
structHash = K(encodedTransaction)
digestPreimage = 0x1901 || domainHash || structHash
txId = digest = K(digestPreimage)
```

`account` and `chainId` appear in both domain and message deliberately. Admission verifies they match the actual executing account and authenticated chain ID; the caller cannot supply the authoritative domain. No additional Ethereum personal-sign prefix is added. EIP-712 is the chosen envelope for the draft's **conceptual** hash, not a claim that the draft already mandates these bytes. [L2 §12; E1]

Canonical binary interchange schemas are:

```text
Tx = (address account,uint256 chainId,uint256 nonce,
      (address target,uint256 value,bytes data,uint8 operation)[] calls,
      uint64 validAfter,uint64 validUntil,bytes32 policyHash,bytes32 metadataHash)
Signatures = (bytes32 signerId,uint16 scheme,bytes signature)[]
```

Encode Tx as one top-level ABI tuple argument and the signature array as one top-level ABI array argument. Sort envelopes by unsigned signerId ascending and reject repeated/out-of-order IDs. Re-encoding equality applies to this interchange form. JSON is an interchange representation, never the digest preimage; represent large unsigned integers as decimal strings, hex-decode bytes, enforce widths, reject unknown fields/types, and derive the digest locally. The draft already requires deriving the digest from transaction data instead of trusting a display hash. [L2 §85]

### Policy binding and signer identities

The existing Vault signs `configEpoch`; the draft does not have that field. To preserve stale-configuration protection without adding a transaction field, this proposal gives the existing `policyHash` an explicit meaning:

```text
policyHash = K(abi.encode(K("LEP100-15 AuthorizationPolicy v1"),
                          uint256(authEpoch), bytes32(rulesHash)))
```

Initialize `authEpoch=1`; use `rulesHash=ZERO32` in the limited base profile. Increment the epoch without wrap on every signer, signer eligibility, threshold or policy change. Require the signed commitment to equal the current commitment at acceptance, approval and execution. Optional external rules must have a deterministic rules hash and their own specification before enablement. The base profile rejects nonzero rulesHash. This is a **proposed clarification**, including a deliberate boundary against illustrative transactions passing `ZERO_HASH` as policy hash. Epoch binding prevents signatures collected before a signer/threshold change from becoming valid under a different configuration. It also avoids claiming compatibility with Vault's separately signed `configEpoch`. [L2 §§12,29–34; L4 typed-data.js:7–20,60–75]

Signer IDs are independent registration slots, not public keys. Proposed assignment is `K(abi.encode(K("LEP100-15 SignerId v1"), account, uint256(registrationSequence)))`; sequence starts at 1, increases without wrap, is never reused, and replacement obtains a new ID. The descriptor maps that ID to exactly one scheme and credential:

- **SECP256K1:** register a validated 65-byte uncompressed SEC1 public key `0x04 || X || Y`; store `public_key_hash=K(publicKey65)` and the address derived as the final 20 bytes of `K(X || Y)`. Verify the recovered signature address against that registered address. The signature carries no caller-selected public key or verifier.
- **CONTRACT_LEP10015_BOOL:** store the registered nonzero native verifier address, with `public_key_hash=ZERO32`; call `is_valid_signature(digest, signature)` under enforced read-only execution and require a canonical true result. Revert, malformed return, unavailable verifier, depth/OOG failure or false means rejection. This is the draft-native interface, not ERC-1271. [L2 §21]
- **CONTRACT_ERC1271 adapter:** store the registered EVM verifier address; enforce STATICCALL, call `isValidSignature(bytes32,bytes)`, and accept only canonical ABI `bytes4(0x1626ba7e)`. A boolean true is insufficient. Enable only when the native-to-EVM adapter and limits have been reviewed. [E5]
- **Native PQ/Ed25519/P-256:** unsupported and rejected; no implicit interpretation of opaque bytes and no fallback to secp256k1. A PQ contract verifier uses a contract scheme/identity above; the algorithm/key validation then belongs to that separately reviewed verifier. The draft requires future migration but makes heterogeneous algorithms optional and supplies examples rather than concrete algorithm parameters. [L2 §§19,75–77]

For counting, reject duplicate signer IDs **and duplicate underlying credential identities across IDs**: secp address for key credentials, `(VM namespace, verifier address)` for contract credentials. Registration cannot give one key multiple threshold votes. Different verifier addresses are distinct credentials; organizational independence remains an owner provisioning responsibility. Ordinary spending rejects RECOVERY roles, inactive descriptors and unsupported AGENT permissions. Initial profile enables KEY/CONTRACT roles only. Revalidate current eligibility and contract validity at execution; an earlier off-chain result is insufficient. [L2 §§7–8,20,22]

### Nonce, revocation and execution transitions

1. `propose`: check caller eligibility, canonical fields, nonempty bounded calls, policy commitment, valid window and nonce capacity. Assign `nonce=next_nonce`, checked-increment, then store the full digest/transaction and nonce-to-digest reservation atomically. Do not consume this reserved transaction yet. The proposal can be executed after later proposals. [L2 §§13,22]
2. Stored-proposal execution: require exact stored digest/fields, current policy, unexpired/noncancelled state, eligible distinct approvals meeting threshold and inclusive timing. Union on-chain approvals and submitted signatures by signer ID so each credential counts once. Do not compare an old reserved nonce to the now-advanced `next_nonce`, and do not increment twice.
3. Direct signed execution: when no reservation exists, require `nonce==next_nonce` and complete threshold signatures. The entrypoint acquires its execution lock before any external verifier. After verification, atomically reserve/increment and mark consumed before executing calls. If a reservation already exists, use the stored-proposal rules and require an exact digest match; never replace a different proposal at that nonce.
4. During execution: hold a transaction-wide account execution lock, mark consumed before any untrusted target interaction, execute calls in order, and commit once. Any target/verifier failure or OOG aborts the complete batch, state, value transfers and events. The consumed marker and direct nonce reservation roll back with the transaction. The earlier reservation of a stored proposal remains. [L2 §§24–25]
5. Cancelled, expired and successfully executed reservations are terminal for nonce reuse. Reject checked increment at `next_nonce=2^256-1`; do not wrap to zero. Concurrent direct transactions racing the same nonce can commit at most one.
6. Revocation before execution removes that signer's on-chain approval and sets a per-proposal off-chain-signature revocation tombstone. Old signatures of that signer no longer count for that proposal. A later explicit on-chain approval can count again; it does not make old off-chain signatures valid again. This is the proposed mechanism for the draft's revocability requirement; a bare boolean approval map would otherwise allow a previously collected signature to restore a revoked approval. [L2 §§22–23]

## Limited first implementation and exact native gaps

The first implementation target is the **base proposal/approval multisig**: secp256k1 KEY signers plus native contract signers, `CALL` batches, chain/account/policy/nonce binding, on-chain approval/revocation, direct signatures, cancellation, threshold and self-authorized signer changes. Start with no agents, recovery spending, AI authorization, optional policy rules, delegate calls, EVM-target calls or native PQ/Ed25519/P-256. Their use must fail explicitly. `STATIC_CALL` transactions and EIP-1271 remain rejected until their respective adapters are implemented. This is a limited implementation target, not full standard conformance; the draft's complete core still requires its supported call, custody and contract-signature behavior and official conformance suite. [L2 §§10,16–25,97,111; L6]

The selected native source is **not already capable of executing this profile**. Its ValueType list contains u64/u256/bool/address/bytes32/string; its instruction set contains context, arithmetic and equality but no contract-visible Keccak or signature verification instruction. Its dynamic envelope provides UTF-8 strings, not arbitrary byte arrays or structs/lists. Existing host calls are typed native invocations, not arbitrary EVM calldata or a transitive static-call mode. [L7, L8, L9]

| Primitive / seam | Existing evidence and required engineering |

## Minimum portable vectors and negative tests

Publish fixed fixtures with expected **bytes**, not self-comparisons generated by the implementation under test. Each positive fixture records domain/type strings, encodedDomain, every encodedCall and callHash, encodedCallList, callsHash, encodedTransaction, structHash, 66-byte digestPreimage, digest/txId, policy epoch/rules hash, registered credentials/IDs, canonical signature envelopes and expected state transitions. Derive expected values with an independently implemented encoder plus a separate EVM/TypeScript oracle, then run the same fixtures through native compiler/runtime, gateway and wallet decoder. Label them proposed until owners accept the profile. [L1; L2 §97]

## Exact external decision remaining

The standards owner/Foundation must **accept, amend or reject this single proposed profile and the corresponding fixed vector set as one versioned artifact**. Acceptance must name the authoritative specification revision, canonical type strings/algorithm registry, zero-expiry clarification, authorization-policy epoch commitment, signer-ID/credential and revocation semantics, nonce transitions, and declared limited implementation boundaries. Existing draft text and Vault SDK behavior are evidence for review, not that decision. No new 12-question exchange is needed.

After that decision, engineering still has to implement the missing native primitives/account and pass the selected native/adapter/client vectors. The official conformance-suite authority and final independent security/release acceptance must be supplied by their owners. This note changes no accepted release source, standard, approval, chain, deployed Vault, LAX or MultX artifact. [L1, L6]
